# OPSTS — Frontend

Static multi-page frontend for the **Online Project Supervision & Tracking
System** at Ghana Communication Technology University. Plain HTML + vanilla JS,
styled with **Tailwind CSS v4**. No framework, no bundler; Tailwind is the only
build step and its output is committed.

> **Rebuild in progress.** The design system (tokens, primitives) and the
> signed-out screens are complete and verified. The portal screens are being
> rebuilt on top of them role by role — student, then supervisor, then admin,
> and until each is done it still carries the old class names and renders
> unstyled. `pages/_kit.html` is the specimen page for the primitives.

## Design decisions

### The brand colours are GCTU's, extracted rather than eyeballed

Every brand value is traceable to a source on the university's own site.

| Token | Value | Where it came from |
|---|---|---|
| `--navy-950` | `#021730` | site.gctu.edu.gh inline theme CSS — deepest section ground |
| `--navy-900` | `#011f41` | same, header bar; the site's own comment reads *"GCTU brand color"* |
| `--navy-800` | `#071a60` | same, section ground |
| `--gold-400` | `#ffc600` | same — button fills, and its **focus outline** (`outline: 2px solid #ffc600`) |
| `--crest-indigo` | `#292866` | the dominant pixel of `themes/gctu/assets/images/logo.png`, decoded and counted |
| `--crest-cream` | `#fbf9cb` | the crest's shield field |
| `--crest-gold` | `#e2a927` | the crest's outer ring |
| `--crest-crimson` | `#a30218` | site CSS, also commented *"GCTU brand color"* |

The remaining steps are interpolated in OKLCH at **hue 264** — the hue the
university's own hero and section grounds already use. The sourced anchors sit
on that hue within 11°, so the ramp reads as one family rather than four
unrelated blues. `gold-400` was generated by the same formula before being
snapped to the sourced value: the formula produced `#ffc700`, one unit off, which
is the check that the hue and chroma choices were right.

Two rules the palette enforces:

- **Navy is structure and primary action. Gold is accent only** — the active nav
  indicator, the focus ring, one key metric, the crest lockup. Never a wash,
  never a full-width button fill. Only `gold-700` clears 4.5:1 for text.
- **`--crest-crimson` is not the danger colour.** A brand red that also means
  "rejected" makes every institutional mark look like an error. Danger is
  `--risk-*`, a separate ramp.

### Type: Fraunces + Inter

**Fraunces** sets display and headings. It is variable with a real optical-size
axis, so one file covers a 20px section heading and a 49px display without
setting large text in small-text shapes — and it carries the institutional
register the crest already establishes. Below 20px it hands off to Inter
(`.type-heading-xs`), because at 16px Fraunces is working under its optical range
and Inter is simply clearer.

**Inter** sets body, UI and numerals, with `font-feature-settings: 'cv05','cv08'`
and `font-optical-sizing: auto`. Those two character variants are not decoration:
`cv05` gives lowercase *l* a tail and `cv08` gives uppercase *I* serifs, which is
the difference between `1`, `l` and `I` being distinguishable in an index number
like `04220231D` and not.

Numerals are `tabular-nums` in every column — tables, versions, percentages,
counts. A ragged `100%` under a `40%` is a bug you can see.

Scale: 12 / 14 / 16 / 20 / 25 / 31 / 39 / 49, with `clamp()` on the two display
sizes. Line heights 1.15 display / 1.3 heading / 1.55 body / 1.4 dense rows.
Body copy caps at 68 characters.

### Fallback metrics

Both families are self-hosted (latin + latin-ext woff2, `font-display: swap`) and
the two critical faces are preloaded. Each is shadowed by a metric-matched
fallback face so the swap does not move the text.

The override values were **measured in the browser**, not copied: the same string
was rendered in the real face and the fallback, and `size-adjust` /
`ascent-override` were tuned until both matched. Current state, at 16px and 32px:

| | real | fallback | delta |
|---|---|---|---|
| Inter | 289.59 × 20 px | 289.55 × 20 px | 0.04 px |
| Fraunces | 556.47 × 39 px | 556.56 × 39 px | 0.09 px |

Re-measure with `pages/_kit.html` open if either font is ever swapped.

### Glass is a material with rules

Glass appears in exactly four places: the sticky top bar **once the page scrolls
past 8px**, the notification/command overlays, modal scrims, and the mobile
bottom bar. Cards, tables and forms are solid surfaces — data on frosted glass is
a legibility failure and this app is almost entirely data.

`--glass-bg` collapses to a solid surface under both
`@supports not (backdrop-filter)` and `prefers-reduced-transparency: reduce`.

### Motion

Durations are the product's (120 / 180 / 240 / 320 ms — nothing over 400). The
easing curves are Material 3's published tokens: `cubic-bezier(.2,0,0,1)`
standard and entering, `cubic-bezier(.3,0,1,1)` exiting,
`cubic-bezier(.05,.7,.1,1)` decelerating. Only `transform` and `opacity` are
animated. List entrances stagger 24ms per item, capped at eight.

`prefers-reduced-motion: reduce` drops every duration to 0.01ms at the token
level, so it applies everywhere at once rather than per-component.

### Accessibility floor

- WCAG 2.2 AA. Verified by script over the rendered specimen page in **both**
  themes: 186 text nodes, zero failures.
- The focus ring is **two-tone**. A gold ring alone measures 1.58:1 on white and
  fails SC 1.4.11, so `--focus-ring` is gold wrapped in a dark halo, which clears
  3:1 against whatever it lands on. `:focus-visible` only.
- 44px minimum hit target (`--hit-target`), responsive from 360px, verified for
  horizontal overflow — wide tables scroll inside `.table-wrap`, the body never
  does.
- Semantic HTML first: real `<table>`, real `<button>`, real `<label>` tied to
  every input, errors tied by `aria-describedby` and driven off `aria-invalid`.
- Status is never colour alone. Every lozenge carries a word and a glyph.

## Patterns taken from Atlassian Design System

The primary reference, because ADS is built for this exact class of product —
multi-role work tracking with queues, statuses, assignment and review.

**Adopted**

- **Token layering.** Raw palette → semantic roles → utilities. Components only
  ever touch the semantic layer, which is what makes the dark theme a re-point of
  ~40 variables instead of a `dark:` on every element.
- **Elevation as surfaces, not tints.** `surface` / `raised` / `overlay` /
  `sunken` are the same colour; depth is carried by a two-part shadow. ADS's
  raised shadow is two offsets at different radii; ours is the same structure,
  retinted to `--navy-950`.
- **Lozenge** for status — compact, bounded, one per meaningful attribute.
- **Empty state** structure: heading, one line of explanation, the action that
  resolves it. Designed before the populated state.
- **Banner** for a page-level condition that outlives the page — exactly the
  `must_change_password` case.
- **Section message** for the result of what the user just did.
- **Side navigation** with sections and a selected state.
- **Metric type role.** ADS has `font.metric.*` distinct from `font.heading.*`;
  a figure is not a heading — it is tabular, tight and never wraps.
- **Space scale**, 4-based: 2 / 4 / 6 / 8 / 12 / 16 / 20 / 24 / 32 / 40 / 48 /
  64 / 80.
- **Voice.** Sentence case, no exclamation, no "Oops". The API's own messages
  already read this way, which is why they are surfaced verbatim.

**Departed from, deliberately**

- **Colour.** ADS's primary is `#1868DB`. The client's is GCTU's navy. Nothing
  of Atlassian's hue survives.
- **One family for heading and body.** ADS uses Atlassian Sans for both. This app
  pairs a serif display with a sans body, because a university portal that looks
  like Jira looks like nothing in particular.
- **Lozenges carry an icon.** ADS's are colour + text. A supervisor scanning a
  queue on a projector needs the third channel.
- **Success is green, not lime.** ADS's post-refresh success ramp is lime
  (`#5B7F24`); beside a navy/gold brand it reads as a fifth accent rather than a
  state.
- **Body size.** ADS bodies at 14px. Reading copy here is 16px with a 68ch
  measure; 14px is kept for dense table rows and UI chrome.
- **Glass.** ADS has none. The four permitted uses come from the project brief.
- **Only statuses the API can emit.** No "Moved", no "New", no "Discovery" — and
  no chapter state the backend does not store (see below).

Motion specs come from Material 3, restraint from Geist, and "hierarchy through
weight before size" and "design the empty state first" from Refactoring UI.

## The signed-out screens

`index.html` (sign in + register), `forgot-password.html`,
`reset-password.html`, `change-password.html`, `pending.html`.

Four things worth knowing about them:

- **`reset-password.html` must stay at the root.** `Backend/src/services/email.js`
  builds the link as `APP_URL/reset-password.html?token=…`. Moving or renaming
  the file breaks every reset email already sent.
- **The waiting room is reached from a 403, not a successful sign-in.** The brief
  says a pending user "can sign in but sees nothing"; the backend disagrees —
  `authController.login` throws `403` for `status = 'pending'`. So `pending.html`
  is routed to from that specific response and from a successful registration,
  and it carries the server's own sentence. There is no red on it and nothing is
  asked of the reader, because nothing is wrong.
- **`?next=` is filtered.** Handing a query parameter to `location.replace()`
  makes the sign-in page an open redirect. Only a same-origin absolute path is
  accepted; `//evil.example` and `/\evil.example` are rejected with the rest,
  since browsers read both as another host.
- **`mustChangePassword` is a locked door.** `session.js` sends every other page
  to `change-password.html` until it is cleared, and the banner there is not
  dismissible. After the change the server issues a new token — it bumped
  `token_version`, retiring the one in the tab — so the client swaps it before
  its next call, then re-reads `/auth/me` rather than assuming the flag is gone.

Verified in the browser, both themes: zero contrast failures across sign in,
register, waiting room and change password; the gradient panel measured against
the *lightest* stop of its own gradient (worst case 5.67:1 on the motto). No
horizontal overflow at 360px. Every touch target ≥44px under `pointer: coarse`.

One bug this pass found and fixed: a property that transitions a `var()` does not
reliably re-resolve when the custom property changes, so toggling the theme left
selected tab labels at the light `--text` on a dark panel — a measured 1.12:1,
permanently. Transitions are now suppressed for the single frame the swap takes
(`[data-theme-switching]` in `base.css`), which also makes the switch instant.

## Where the brief and the backend disagree

Recorded rather than silently resolved:

| Brief says | Backend actually does |
|---|---|
| feedback decision is *approved / revisions requested / rejected* | `feedback.rating` is `CHECK (rating IN ('Approved','Needs Revision'))` — there is no rejected. "Rejected" exists only on `projects.topic_status`. |
| chapter states *locked / draft / submitted / under review / revisions / approved* | Nothing gates a chapter behind the previous one and no draft is stored. The real states are **not started / under review / needs revision / approved**, plus an overdue overlay from the milestone `due_date`. |
| route list | omits `GET /projects/milestones/:projectId` and `PUT /projects/milestones/:id`, which the progress timeline needs. |
| a pending user "can sign in but sees nothing" | `POST /auth/login` throws `403` for `status = 'pending'`; they cannot get a token at all. The waiting room is routed to from that response instead. |

The tracker is built to the backend, not the brief. A stop that showed "locked"
or "draft" would be the interface telling the student something the system does
not know.

## Running it

```bash
npm install
```

```bash
npm run serve
```

That runs `serve.js` on **port 5500**, which is the port `CORS_ORIGINS` and
`APP_URL` in `Backend/.env` already name — so the API accepts calls from it and
password-reset emails point back at it. Use another port and every request comes
back 403 from the CORS guard, with a message saying exactly that.

`serve.js` exists rather than `python -m http.server` for one reason beyond the
port: it sends `Cache-Control: no-store`. Python's server sends no cache headers
at all, so the browser applies heuristic freshness from `Last-Modified` and keeps
running an edited `.js` from disk cache without revalidating — you reload, watch
the old file execute, and get no error telling you that is what happened.

While editing CSS, in a second terminal:

```bash
npm run dev
```

For a one-off minified build:

```bash
npm run build
```

The API root is `API_BASE_URL` at the top of `js/config.js` — one constant, and
it is the only thing a deployment needs to change.

### Why the built CSS is committed

The app deploys as static files, so a clone with no Node toolchain still has to
render. **Re-run `npm run build` and commit the result whenever you change
anything in `src/`**, or the deployed styling silently lags the source.

## Source layout

| File | Holds |
|---|---|
| `src/input.css` | Tailwind entry point — imports the three below |
| `src/tokens.css` | Palette → semantic roles → `@theme inline` → dark theme |
| `src/base.css` | `@font-face`, element defaults, focus, forms, tables |
| `src/components.css` | The primitives: buttons, lozenges, fields, messages, empty states, skeletons, modal, menu, nav, tracker |
| `src/auth.css` | The signed-out screens: split shell, role picker, waiting room |
| `pages/_kit.html` | Specimen page. Every primitive, both themes, live token swatches |

### Scripts

Loaded in this order on every page; each depends only on the ones before it.

| File | Holds |
|---|---|
| `js/theme.js` | Light/dark, in `<head>` before first paint |
| `js/config.js` | `API_BASE_URL`, role home paths, department list |
| `js/session.js` | Session storage and the route guards |
| `js/api.js` | The fetch wrapper, bearer token, 401 handling, authenticated downloads |
| `js/ui.js` | Icons, toasts, busy buttons, field-error plumbing |
| `js/auth.js` | One controller per signed-out screen |

### Tokens are declared twice, on purpose

```css
:root { --action: #1f4192; }                     /* 1. runtime variable */
@theme inline { --color-action: var(--action); }  /* 2. Tailwind utility */
```

1. The **plain custom property** is the contract with the JavaScript. The portal
   scripts build markup as HTML strings containing `style="color:var(--text-subtle)"`.
   Values may change freely; names may not.
2. **`@theme inline`** republishes the value under Tailwind's namespace so
   `bg-surface` / `text-subtle` exist. `inline` is what makes the utility compile
   to `var(--action)` rather than a frozen hex — which is why utilities follow
   the theme swap for free.

Dark mode re-points the variables; it is not a `dark:` prefix on every element.
`data-theme` is written on `<html>` before first paint, and with no stored choice
the OS preference applies.
